## Inspected upstream paths (before the replacement)

### Exact file read

`main.ts` creates services and calls `createAgentSessionFromServices()` → `sdk.ts:createAgentSession()` → `new Agent()` with `ModelRuntime.streamSimple`. Interactive submissions call `AgentSession.prompt()` (also used by print/RPC). Input hooks and template/skill expansion currently precede message creation. `_runAgentPrompt()` calls `Agent.prompt()` → `loopController.run()`; without an injected controller this calls `runAgentLoop()`.

`agent-loop.ts:streamAssistantResponse()` forwards provider deltas as message events. It waits for the complete assistant response before examining tool calls. `executeToolCalls()` resolves a tool, applies `prepareArguments`, validates TypeBox arguments, invokes session `beforeToolCall`, then `executePreparedToolCall()` calls `AgentTool.execute()`. `wrapRegisteredTools()` supplies a current extension context. Built-in `read` resolves the requested path against that context's cwd, checks accessibility, reads bytes, and returns a bounded text/image result. A missing file throws; the executor preserves the error message as an error tool result. The result emits `message_end`; `AgentSession._handleAgentEvent()` appends it to the JSONL transcript. The stock loop then asks the provider again and finishes on a no-tool turn unless hooks/queues continue it.

### File write/edit

The provider's complete tool proposal follows the same validation/hook path. `write.ts` resolves the path, enters `withFileMutationQueue()`, creates parent directories and uses `fs.writeFile`. `edit.ts` enters that queue, reads the original, preserves BOM/line endings, computes all replacements against that original, then uses `fs.writeFile`. Render details retain a diff and unified patch. Abort checks hold the in-process queue until a filesystem promise settles, but an abort after mutation can still throw despite changed bytes.

The queue keys existing paths by `realpath` and serializes cooperating calls in this process. It is not a cross-process lock, preimage compare-and-set or atomic replacement. There is no prepared preimage binding at the main loop boundary. Phase 2 must carry a real preimage and guard the actual replacement, and must describe the remaining race against non-cooperating writers instead of claiming universal filesystem atomicity.

### Tool/test failure

`bash.ts` spawns the selected shell with cwd/environment and streams combined stdout/stderr into `OutputAccumulator`. A nonzero exit returns `isError: true`, preserved output and structured `exit_code`/`wall_time_seconds`. The executor retains result details and emits `tool_execution_end` and a persisted `toolResult` with `isError`. Validation and thrown exceptions become error text. No built-in dedicated Git/test controller exists: they are shell commands.

`afterToolCall` and `message_end` extension handlers can replace results/messages today. Kernel evidence must capture authentic raw results before these display/model transformations; an extension replacement cannot serve as authoritative observation or modify instruction history.

### Timeout/interruption

Shell timeout/abort kills the process tree and waits for process settlement. The shell tool throws output plus a timeout/abort message. This does not prove no effects occurred. `Agent.abort()` passes an AbortSignal to provider/tools; read cancellation is observational, while write/edit cancellation may arrive after a filesystem effect. Current session JSONL saves completed messages, not a durable operation start. A crash after mutation but before the result leaves no authoritative operation lifecycle record.

Phase 2 must commit a stable operation ID, final policy decision and reservation/start transition before dispatch; capture failed/partial/uncertain outcomes; recover an unresolved effectful start as OUTCOME_UNKNOWN; never blindly repeat it. Registered authoritative digest/idempotency reconciliation may resolve a narrow operation; the full manager remains Phase 3.

## Actual replacement seam

The Phase 1 `AgentLoopController` replaces both stock prompt and continuation loops. Implement the Sandhāna controller there, retaining `declareToolChanges` and provider streaming infrastructure, but not using the stock batch dispatcher as a rival action authority. The controller must own candidate selection, governed operation dispatch, continuation and final reports while emitting compatible Agent lifecycle events for session/TUI consumers.

Default mount belongs in the coding-agent session construction/runtime, not a second process or prompt-only extension. Reusable agent-core may retain its stock library surface; tools exposed to a Padma mission must not retain a callable unguarded primitive executor. Complete provider JSON must validate before dispatch; multi-tool proposals must reserve/authorize serially against current mission revisions.

Additional seams that must not bypass it:

1. `AgentSession._executeNestedToolCall()` currently calls exported `runToolCall()` using the callable registry (including deferred/CodeMode tools). Wrap/adapt the registry and route nested execution into the same mission dispatcher and budget; unknown/unreviewed tools cannot gain structural provenance by name or schema alone.
2. `_runAgentPrompt()` / `_handlePostAgentRun()` / `_runBeforeSettleBoundary()` can independently call `Agent.continue()` after retries, compaction, queues or extension continuation. Preserve useful infrastructure, but route proposals into kernel decisions and retain the same mission/accounting. A terminal report forbids post-terminal continuation of that mission.
3. `AgentSession.executeBash()` directly invokes `executeBashWithOperations()`. Interactive `handleBashCommand()` and RPC `bash` first run `user_bash` hooks; a hook may return a supposedly complete result instead of operations. Manual shell dispatch also needs a governed command/operation; imported results are not proof of a kernel dispatch.
4. `sdk.ts` starts `CacheWarmer` model requests separately; compaction, virtual model routing, branch summaries and nested tools may consume additional model usage. Requests during a mission belong to its ledger, including retries. Context projections remain views, not mission authority.
5. Input transforms, skill expansion, extension-generated user messages and mutable message-end hooks must not overwrite or impersonate the immutable original user input or scoped authorization. Bind trusted input provenance before transformations; model-facing derived text does not confer additional permission.

The pinned revision has project trust for loading resources and extension tool-call hooks, but no built-in filesystem/process permission system. Sandhāna therefore needs an actual base ScopePolicy rather than assuming an existing approval API. Preserve sandbox/remote adapters through reviewed registrations, exact environment bindings and intersecting policy; do not classify a remote override as the reviewed local adapter merely because both are named `read` or `write`.
